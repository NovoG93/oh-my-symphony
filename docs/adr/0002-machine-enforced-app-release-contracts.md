# Machine-enforced application release contracts

## Decision

An `app-release` label opts a file-board Verify ticket into a host-owned release gate against the repository-root `release-contract.yaml`; an `app-release-finalizer` label identifies the named delivery ticket. After opt-in, durable SQLite identity is authoritative even if a worker removes the labels. The host resolves the configured local branch, reads the contract from that exact commit, requires byte-identical workspace contract content, and hashes every declared regular runner source against both the target blob and workspace file. Evidence must use the contract's exact runner command and bind strict native JSON, exact check/status coverage, coherent exit semantics, implementation-branch ancestry, and contained non-empty hashed artifacts to the approved target SHA. This preserves every non-app workflow while preventing an old Markdown `GREEN` verdict or mutable worker-side runner from approving a changed target.

Each cycle has a host-created generation and is bound to the exact active verifier run that began after the pending record. GREEN atomically upgrades that tuple to approved. The finalizer then requires the same generation, verifier, contract hash, target branch and SHA; no live verifier lease; an exact bound finalizer run; and host-recorded terminal completion. Authority is rechecked before the backend and every turn. A continuation within the already bound live verifier run may use that approval. Redispatching an approved verifier after restart invalidates it, creates a new generation, returns it to Verify, and requires fresh evidence.

## Fresh verifier and repair decision

A repairable failure is grouped by the contract's stable repair groups. On the atomic file-board tracker, Symphony creates or fully reconciles one repair ticket per group and one fresh verifier blocked by those repairs. Before each file create, the host persists a deterministic ticket reservation keyed by finalizer, release fingerprint, role, and repair key. A crash after create, concurrent service, or stripped labels therefore resumes the same ticket instead of allocating a duplicate. The fresh verifier records the release fingerprint, expected contract hash, and finalizer binding in diagnostic labels, while SQLite remains authority. The finalizer replaces only source/previous verifiers bound to that same lineage while retaining unrelated dependencies before the failed verifier may close as historical evidence. App-release verifier execution itself is file-board-only: other adapters refuse labeled cards before a run lease or agent turn because they cannot provide the same durable lifecycle boundary. Ordinary remote boards that have not opted in remain unchanged and quiet in doctor output.

Terminal cleanup is also host-owned. Startup reopens stale or unproven terminal release state. Before committing or removing a lingering release-evidence workspace, it acquires and heartbeats a dedicated cleanup lease, then re-reads the gate. A live peer run prevents cleanup, and the cleanup lease prevents concurrent gate replacement.

Finalizer completion binds the exact host-observed terminal ticket version, not merely its identifier or state. Symphony checks the file token before the terminal authority guard, immediately before the SQLite completion write, and again after persistence. Any intervening rewrite atomically replaces the approval with a fresh pending generation and reopens verification; stale completion cannot be replayed.

## Upgrade and target boundaries

The provenance migrations create an online SQLite backup beside `.symphony/state.db` when release-gate rows already exist. They assign new generations, record durable evidence and lifecycle-item identity, and deliberately convert legacy pending, approved, or completed rows to fresh pending cycles when older rows cannot prove exact-run or exact-ticket-version completion.

"Current target" means `refs/heads/<configured branch>` in the local workflow repository. Symphony does not fetch, compare a remote ref, or discover a deployed revision. Operators must synchronize that branch before verification and serialize external target writers during finalization. Declared external runners, browsers, deployment systems, and any side effect they perform during one agent turn remain outside the SQLite transaction.

## Consequences

Malformed, missing, unsafe, stale, or internally contradictory evidence rewinds the same verifier without creating product work. A nonzero exit is valid only when the exact native/evidence statuses contain a FAIL, and produces no separate exit-code repair. Product check, console/network, and ancestry failures create repair work only where the atomic file-tracker lifecycle is available. A labeled remote transition is refused before a lease or turn; Symphony neither rewinds that remote card nor mutates its lifecycle, so an already-advanced card requires operator repair. The manual `symphony release check` command is read-only validation and does not create lifecycle authority. Hashing the declared runner sources narrows accidental and worker-side mutation, but deliberately external tooling and its runtime remain a trust boundary; independent operator browser QA remains required for final acceptance.
