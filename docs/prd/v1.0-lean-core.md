# PRD: oh-my-symphony v1.0 — Lean Core

- **Status:** Draft v4 (supersedes the v3 "≤2,200 LOC rewrite" draft)
- **Baseline:** v0.27.0, `main` @ `c73b6cc` (2026-10-17)
- **Goal in one line:** cut what operators and contributors must read, install, and maintain, without removing any shipped capability.

## 1. Why the v3 draft was revised

The v3 draft targeted a ≤2,200 LOC rewrite. Measured against the baseline, that
means deleting about 97% of the product, including features shipped in v0.27.0:

| Area (baseline) | Size |
| :--- | ---: |
| `src/symphony/**/*.py` | 76,800 LOC in 149 files |
| `src/symphony/web/static` | 14,984 LOC |
| `tests/` | 91,704 LOC in 140 files |
| Tracked `docs/` | 14,354 lines |
| `README.md` + `README.ko.md` | 1,525 + 1,205 lines |
| Tracked root files | 24 |

A rewrite of that size cannot be reviewed or rolled back, and it would remove
the PM Workspace, `symphony factory`, chat intake, Windows recovery, and the
Linear/Jira trackers. v4 keeps the v3 direction (one engine, thin clients,
external verification, declarative agents) but reaches it by removing
duplication and debris in reviewable steps.

## 3. What counts as bloat

1. **Repository debris:** committed dogfooding state, session handoffs,
   historical plans, release-evidence folders, and quality ledgers. Git
   history and GitHub Releases already keep them.
2. **Duplicate entry points:** four agent instruction files with the same
   content, two terminal launcher scripts that wrap `symphony tui`, and
   two copies of a 1,500-line README.
3. **Generated-artifact pipelines:** the bilingual PDF manual build.
4. **Duplicate code paths:** backend classes that differ only in a command
   string and flags; dead functions; a 10,474-line `orchestrator/core.py`.

## 4. Requirements

### LR-1 Repository surface (Phase 1)

- Delete `.sdlc/`, `.impeccable/`, `HANDOFF.md`, `CONTEXT.md`,
  `QUALITY-LEDGER.md`, `.quality.md`, `docs/plans/`, `docs/handoffs/`,
  `docs/quality/`, `docs/spec/`, `docs/changelog/`, `docs/features/`, and
  other one-off design and handoff notes. Links that cite them as release
  evidence point to the `v0.27.0` tag instead.
- One instruction file per audience: `AGENTS.md` for this repo and
  `AGENTS.md` for bootstrapped projects. Drop `GEMINI.md` and
  `GEMINI.project.md`; Gemini users set `context.fileName: AGENTS.md`.
- Delete `tui-open.sh` and `tui-open.bat`. `symphony tui` already runs
  the doctor preflight and reports the process holding the port.
- Delete the PDF manual pipeline (`docs/manual/`,
  `scripts/build_manual_pdf.py`, `scripts/sync_manual_tables.py`, and its
  Pages CI steps). The Pages landing page stays.
- `README.md` and `README.ko.md` become quickstarts of at most 250 lines.
  Reference material moves to `docs/reference.md` without loss.

### LR-2 Declarative agent profiles (Phase 2)

- Backends that only differ by command and flags (`agy`, `kiro`, and future
  plain CLIs) are expressed as profile data:
  `cmd`, `resume_flag`, `unattended_flags`, `format: text|ndjson|jsonrpc`.
- Adding a 9th plain-text CLI needs 0 lines of Python.
- Stream protocols with real parsing (`codex` JSON-RPC, `claude`, `pi`,
  `opencode`, `prime-agent` NDJSON) keep their modules.
- Existing `agent.kind` values and per-kind config blocks keep working.

### LR-3 Dead code and monolith split (Phase 2)

- Remove functions with no callers (verified by `vulture` plus `grep`, not
  by confidence score alone).
- Split `orchestrator/core.py` by responsibility (dispatch, retry, merge,
  continuous-improvement scheduling) with no behavior change. Target: no
  `src/` module over 3,000 lines.

### LR-4 One engine, thin clients (Phase 3)

- The web board and the TUI read and mutate state only through the
  `server.py` REST/SSE API. No client parses `WORKFLOW.md` or touches
  worktrees directly.
- `symphony tui` attaches to a running service on the configured port, or
  starts one, instead of failing on a busy port.

### LR-5 Verification gates and harness learning (Phase 3)

- Forward stage moves require the stage's `verify_cmd` to exit 0; workers
  cannot advance a ticket by editing its frontmatter.
- Failed verifications, stalls, and human rework append to
  `.symphony/traces/<issue-id>.jsonl`.
- Harness-improvement proposals extend `continuous_improvement.py`
  (already proposal-only) instead of adding a parallel `introspector.py`.
  Default: human approval. `auto_apply: true` is opt-in.

## 7. Resolved questions from v3

1. **Jira/Linear:** stay in core (owner decision 2026-02 #4). They are not
   moved to `examples/hooks/`.
2. **Harness upgrade approval:** human approval by default, with opt-in
   `auto_apply: true`.

## 8. Out of scope

- Rewriting to a fixed LOC budget.
- Removing or renaming any feature in section 2.
- Container or bind-mount sandboxing (v3 FR-6 path masking); the existing
  `git_sandbox` guard stays the boundary until a separate design.
